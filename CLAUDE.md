# insight-wave

11-plugin monorepo for consulting, sales, and marketing on Claude Code. Apache-2.0. All plugins follow the Claude Code plugin standard.

### Generated documentation artifacts

The repo-wide documentation-drift audit belongs at `docs/audit-report.md` — that is the single home for audit output, and it is replaced wholesale by a fresh `cogni-docs` audit run rather than hand-edited. A stale header there means the audit is due to be re-run, not patched by hand. `.claude-plugin/` holds the marketplace manifest and nothing else. An older drift report once sat at `.claude-plugin/doc-audit-report.md` and was removed rather than regenerated: nothing in this repo referenced or wrote that path, `docs/audit-report.md` supersedes it, and its plugin roster predated the current marketplace by several retirements. ## Cross-Plugin Conventions

### Script Output Format

All scripts return JSON: `{"success": bool, "data": {...}, "error": "string"}`. Scripts are stdlib-only — bash + python3, no pip dependencies.

### Hook Matcher Conventions

A hook matcher that matches on an **agent name** must accept the plugin-qualified `plugin:agent` form, because that is the string the host dispatches under — a plugin-supplied agent arrives as `cogni-consult:consult-dashboard-refresher`, never as a bare `consult-dashboard-refresher`. Make the qualifier optional rather than replacing the bare name, so both forms match:

```
^(cogni-consult:)?(agent-a|agent-b)$
```

Keep both anchors. The matcher is applied as a search, not a full match, so an unanchored pattern fires for other plugins' subagents too.

A bare-name-only matcher fails **silently**: the hook simply never runs, the script it would have called stays correct, and hook scripts exit 0 on every path — so nothing anywhere raises. The only evidence is the absence of whatever the hook injects. Nothing will report this class of bug for you, and no guard script checks matchers today — so when you add an agent-name matcher, pin both name forms in a suite under the plugin's `tests/`, which CI does run (see Contributing).

### Agent Model Strategy

| Role | Model | Rationale |
|------|-------|-----------|
| Orchestration | sonnet (skill context) | Phase dispatch, sub-question generation |
| Research | sonnet | Web research, section researchers, deep researchers |
| Heavy synthesis | opus | Demanding rewrites (the `copywriter` skill), 60-candidate scoring (cogni-trends) |
| Quality assessment | haiku | High-volume rubric evaluation (3-5 dimensions per entity) |
| Content generation | sonnet | Narrative writers, report writers, content writers |

Research agents report `cost_estimate` in output JSON (input/output words + estimated USD). Orchestrators accumulate these.

### Three-Layer Quality Gate

Most entity-producing plugins follow this pattern:

1. **Structural validation** — scripts check JSON schema compliance
2. **Quality assessment** — LLM-based haiku agents evaluate content dimensions
3. **Stakeholder review** — LLM agents simulate 3 reader perspectives; verdict: accept/warn/fail

Quality gates block downstream generation when upstream entities fail.

### Data Model Patterns

- Entity slugs in kebab-case, derived from entity names
- Project directory: `{plugin}/{project-slug}/` with manifest at root
- Feature x Market combinations are the core join in cogni-portfolio — they drive propositions, solutions, and competitor analysis
- Source lineage: entity records include `source_url`, `entity_ref`, `propagated_at` for correction cascades
- All entity outputs are Obsidian-browsable markdown with YAML frontmatter

## Plugin Data Flow

```
cogni-knowledge ─→ cogni-workspace ────────────────────────→ cogni-visual
  (research)         (compose + polish)                        (render)
       ↓                                                         ↑
cogni-trends ←──→ cogni-portfolio ──→ cogni-sales            cogni-website
  (TIPS scout)     (IS/DOES/MEANS)     (Why Change)          (static site)
       ↑                ↓
  cogni-consult      cogni-marketing
  (action-field WBS) (content engine)

cogni-workspace ← any plugin (claim verification, correction propagation)
cogni-workspace → all plugins (env vars, themes, MCP servers, health)
```

Key integration patterns:
- **Claims propagation**: Research agents auto-log claims with `entity_ref` provenance to `cogni-claims/claims.json`. After verification, corrections propagate back to entity files and cascade staleness downstream.
- **Trends ↔ Portfolio bridge**: `trends-bridge` imports TIPS solution templates as portfolio features; portfolio anchors enrich solution relevance scoring.
- **Narrative citation bridge**: `bridge-citations.py` converts `[Source: Publisher](URL)` inline citations into per-source markdown files before narrative Phase 1.
- **Theme inheritance**: All visual plugins read theme from cogni-workspace via `pick-theme`. Design-variables pattern produces themed CSS custom properties.

## Version Management

**Do not bump a version in a feature branch.** The patch bump is applied post-merge, automatically, per plugin actually touched.

- Plugin version lives in `.claude-plugin/plugin.json` `version` field (semver), mirrored on the plugin's entry in the repo-root `.claude-plugin/marketplace.json` — Claude Desktop reads the marketplace copy for update detection, so the two must always agree
- `.github/workflows/cogni-version-bump.yml` owns the bump. On every push to `main` it patch-increments each plugin the merge touched, editing **both** manifests in one `bump(...)` commit. `scripts/apply-version-bump.py` does the edit; nothing is written unless the rewritten JSON re-parses and differs *only* in the intended version values
- A feature branch that still touches a version reintroduces the merge-conflict class the post-merge move eliminated: when every PR bumped at authoring time, the instant one PR merged, every other open PR's version lines became a textual conflict. insight-wave had it worse than a one-manifest-per-plugin repo, because marketplace.json is a single file all 11 plugins share — so the conflict was repo-wide, not per-plugin
- `scripts/check-version-bump.py` enforces this at PR time (CI: "Version-bump gate" in `.github/workflows/lint.yml`). It flags `version-touched` on any version change vs the fork point, and `version-mirror-desync` whenever plugin.json and marketplace.json disagree. Fix a `version-touched` finding by reverting the version line in **both** files
- The auto-bump is patch-only and structurally cannot cross a maturity boundary, so `maturity` and the maturity keyword in `keywords[]` are never touched by it. **Boundary crossings stay human** — make them on a `bump/…` branch, which the PR-time gate exempts

### Plugin Maturity Model

Maturity is **hard-derived from the version** — no manual maturity field in plugin.json. Full reference: `cogni-docs/references/maturity-model.md`.

| Stage | Version Range | User Expectation |
|-------|--------------|-----------------|
| **Incubating** | `0.0.x` | Skills may change or be removed at any time |
| **Preview** | `0.x.x` (x≥1) | Core skills defined but may change. Feedback welcome |
| **Released** | `1.x.x` | Stable API. Breaking changes only at major bumps |
| **Established** | `2.x.x+` | Proven, deep ecosystem integration |
| **Archived** | Any + `"archived": true` | Security patches only |

**Maturity boundary crossings**: Bumping from `0.x` to `1.0.0` transitions a plugin from Preview to Released — this is a stability contract. Bumping to `2.0.0` signals Established. Be intentional about crossing these boundaries.

**README callout**: Each pre-1.0 and archived plugin has a maturity callout blockquote after the H1 title (e.g., `> **Preview** (v0.x) — core skills defined but may change.`). doc-generate injects this automatically. doc-audit Check 13 enforces consistency.

## README Conventions

Plugin READMEs follow a 16-section IS/DOES/MEANS structure:

| # | Section | Category |
|---|---------|----------|
| 1 | Title + maturity callout + first paragraph | mixed (callout auto-generated, pitch hand-written) |
| 2 | Why this exists | hand-written (problem table) |
| 3 | What it is | hand-written (IS expanded) |
| 4 | What it does | auto-generated (from SKILL.md) |
| 5 | What it means for you | hand-written (MEANS) |
| 6-7 | Installation, Quick start | auto-generated |
| 8-10 | Try it, Data model, How it works | hand-written |
| 11-13 | Components, Architecture, Dependencies | auto-generated |
| 14 | Custom development | hand-written |
| 15-16 | License, Built-by footer | auto-generated |

Use `cogni-docs` skills to manage: `doc-audit` detects drift, `doc-generate` fixes structural sections, `doc-sync` aligns descriptions, `doc-power` strengthens messaging.

## MCP Servers

| Server | Plugins | Purpose |
|--------|---------|---------|
| excalidraw | cogni-portfolio, cogni-workspace | Diagram rendering (infographics, concept diagrams, architecture) |
| claude-in-chrome | cogni-website, cogni-workspace | Browser automation (verification, preview, theme extraction) |
| pencil | cogni-website, cogni-workspace | Web narrative, storyboard, poster, hero rendering |

Managed by `cogni-workspace:install-mcp`, which installs each server on demand and writes it into the user's own config — the top-level `mcpServers` in `~/.claude.json` for Claude Code, `claude_desktop_config.json` for Claude Desktop — pointing at `$HOME/.claude/mcp-servers/{name}/start.sh`.

**No plugin ships a `.mcp.json`.** A checked-in declaration asserts machine state the repo cannot guarantee: the server is spawned at session start even where it was never installed, and it fails visibly there. A second plugin declaring the *same* server name is worse than redundant — the client disambiguates by plugin-qualifying the tool names, which silently dead-matches any `mcp__<server>__.*` hook matcher, with nothing in CI reporting it. `cogni-workspace/tests/test-mcp-declaration-hygiene.sh` enforces the rule.

## Contributing

- CLA required on first PR to core plugins (CLA Assistant bot prompts on PR)
- Feature branches from `main`; one feature or fix per PR
- Do **not** bump `plugin.json` / `marketplace.json` versions in the branch — the post-merge workflow applies the bump (see Version Management)
- Validate skill names with `cogni-workspace/scripts/check-skill-names.sh` before PR
- Plugin and repo-root `tests/*.sh` are CI-enforced — `scripts/run-plugin-tests.py` (CI: "Plugin test suites (discover and run tests/*.sh)" in `.github/workflows/lint.yml`) discovers `tests/*.sh` and `*/tests/*.sh` and fails the build on any non-zero exit. Run the full sweep locally with `python3 scripts/run-plugin-tests.py`, or one plugin's with `--filter <plugin>`. A suite only needs to exit non-zero on failure, run as `bash <path>` with no arguments, and touch no network — the runner reads exit status and nothing else. The no-suites-is-a-failure rule keys on the **pre-filter** discovered population: a discovery that finds nothing means the globs stopped matching and still exits 1 — a floor that holds even when `--filter` is supplied — while a `--filter` narrowing a real discovery down to nothing is an empty query and exits 0 with `data.total: 0`. Three plugins ship no `tests/` of their own — `cogni-marketing`, `cogni-sales` and `cogni-website` — so filtering to one of them is an ordinary empty result; never answer it with a filler suite that asserts nothing. A second consumer reads the same condition differently, and retiring a plugin's last suite must account for it: the handoff preflight in the managed-service repo derives its per-plugin floor **from the base ref**, so it is the *transition* that trips, not the end state. The PR that removes a plugin's final suite is blocked once, and is cleared with the global `COGNI_PREFLIGHT_MIN_SUITES` lever — deliberately global, so the waiver is conscious rather than scoped and standing. Once that PR is on `main` the plugin's derived floor is 0, the named `no_suites_at_base` skip applies, and subsequent PRs touching it pass unblocked, exactly as they already do for `cogni-marketing` and `cogni-sales`. So the cost of a retirement is one conscious lever use on the transition, not a standing tax on that plugin's contributors
- Keep maintainer breadcrumbs out of SKILL.md / agent files — `scripts/check-breadcrumbs.py` (CI: "Maintainer-breadcrumb guard" in `.github/workflows/lint.yml`) fails on newly introduced issue/PR refs (`#NNN`), version tags, or milestone/slice/finding codes. It ratchets against `scripts/baselines/breadcrumb-baseline.json`, so only *new* breadcrumbs trip it; fix by removing the breadcrumb and stating the rationale semantically (provenance lives in git history, CHANGELOG, and `references/`)
- Every `.github/workflows/*.yml` and `*.yaml` must load and declare jobs — `scripts/check-workflow-yaml.py` (CI: "Workflow-YAML guard (every .github/workflows file parses)" in `.github/workflows/workflow-guard.yml`) flags an unquoted plain scalar carrying a colon-space (the shape that makes a file unparseable, silently taking *every* job in it offline rather than failing one step) and a file that declares no jobs. Stdlib-only, no pip dependency; suite at `tests/test_check_workflow_yaml.sh`. It lives in its own workflow on purpose — a guard hosted inside `lint.yml` could never report `lint.yml` failing to load, because the job holding it would not run either
- No discovered test suite may emit an escape-wrapped `PASS:`/`FAIL:` result line — `scripts/check-result-line-plainness.py` (CI: "Result-line plainness guard (no escape sequence in discovered suites)" in `.github/workflows/lint.yml`) flags an escape literal anywhere in a `tests/*.sh` or `*/tests/*.sh` file, and separately flags a `red()`/`green()`-class emitter defined with a coloured body *even when its call-site label lines are clean* — the copy-an-emitter-into-a-new-suite path. A colour before the label defeats a mutation harness's `^[[:space:]]*FAIL:[[:space:]]+<case>` match, so a genuinely red case reports `case_not_found`. Fix by writing the emitter to `printf '%s\n' "$1"`, never by gating it on a capability probe (that makes parsability depend on where the suite runs, and the colour returns under a pty). Hard clean zero — no baseline, allowlist or skip marker; suites parked one path segment deeper are out of scope by glob depth, not by exclusion. Stdlib-only; suite at `tests/test_check_result_line_plainness.sh`
- An agent body may only call MCP tools its own frontmatter grants — `scripts/check-mcp-tool-grant.py` (CI: "MCP agent-grant guard (agent bodies call only servers their frontmatter grants)" in `.github/workflows/lint.yml`) asserts repo-wide that every affirmative `mcp__<ns>__<tool>` token in an agent body is granted by that agent's `tools:` frontmatter, and that every plugin granting a *registered* namespace appears in that server's `required_by`. Detection keys on an **affirmative call site, never prose**: agents elsewhere DISCLAIM a server in the same phrasing ("no Excalidraw MCP"), so a `<X> MCP` heuristic reads them as offenders on day one. It parses all three `tools:` forms — bracketed array, bare comma list, and YAML block list; the block form is load-bearing, not a nicety, because most agents carrying a real call site declare tools that way and a `tools:`-line-only reader reports them as false offenders. The namespace token class admits **hyphens** — real namespaces here are spelled `claude-in-chrome`, and an `[A-Za-z0-9_]`-only class matches none of `mcp__claude-in-chrome__navigate`, going blind to a whole namespace with every case still green. Registry key to namespace is read from `desktop_config_key` as data, never by stripping an `mcp_` prefix. A **second affirmative arm** is keyed on the registry's `provides_tools[]`: an agent body naming a registry tool's bare name **inside a backtick code span** must grant a tool of a server that provides it, resolved at server level. The code span is the mechanical context requirement — bare names like `get_screenshot` and `export_scene` are ordinary English, so matching them in running prose is the false-positive class that once kept a prose heuristic plugin-scoped. This arm **replaced** that plugin-scoped prose detector rather than joining it, which is why no second scope or second suite survives. Do not re-derive the arm's rules here: the guard's own module docstring owns the mechanism, the measurement behind the adoption, and the residual classes it knowingly does not cover — a second copy in this file is a second thing to drift, and the measurement is a snapshot that the next registry entry invalidates. Registry-accuracy gaps take a **non-failing** channel and never move the exit code: a granted `mcp__<registered-ns>__<tool>` whose bare name is absent from that server's `provides_tools[]` is surfaced as an observation, while a registered server carrying no `provides_tools[]` at all is an **error** rather than a narrowed vocabulary — the docstring owns why the two differ. Zero discovery is a failure, not a clean zero. Hard clean zero — no baseline, allowlist or skip marker; suite at `tests/test_check_mcp_tool_grant.sh`
- A test suite may assert on the literal text of a message one of this repo's own scripts emits, but must assert on foreign tool output **by shape** — exit status, stream emptiness (`[ -s "$err" ]`), numeric form or match count — never by wording. Bash and the GNU tools gettext-localize their diagnostics, so a `grep` for an English fragment of, say, an arithmetic-syntax error matches nothing on a non-English host: the red case then passes against unfixed code and the guard reports green while guarding nothing, everywhere except an English-locale CI. There is deliberately no guard script for this and none should be added — own-emitter versus foreign-emitter literals are not statically decidable, so a checker would fire on every legitimate own-emitter assertion; this rule is convention-plus-review, enforced when a suite is written and when its diff is read. A repo-wide or runner-level `LC_ALL=C` pin is **not** the remedy either: `scripts/run-plugin-tests.py` spawns each suite as `bash <path>` with no `env=`, so a pin there covers the CI path only while suites also run directly under the mutation harness — leaving a guard green in CI and still vacuous under the very harness meant to prove it discriminates. Every `LC_ALL=C` this repo's suites already carry pins collation for `sort`/`comm` — the two exports in `cogni-visual/tests/test-arc-taxonomy-sync.sh` and `cogni-visual/tests/test-de-ascii-orthography.sh`, and the inline `LC_ALL=C sort` in `tests/test_release_bundle_wiki.sh` — never message locale
- Generic skill names (`setup`, `scan`, `resume`, `dashboard`, `verify`) must be prefixed with the domain term
